# Варианты размещения и интеграции VpnGuard

**Выбор для 2.0 — Standalone Service (A) на Ubuntu Server 24.04 LTS.** Для первого внешнего потребителя достаточно отдельного процесса и ограниченного контракта диагностики. При появлении общего источника классификации предпочтителен постепенный переход к Hybrid (C). Embedded (B) стоит пересмотреть, если измерения покажут, что межпроцессная передача данных мешает работе, а общий хост сможет гарантировать независимое завершение модулей. В 1.9 время жизни агента совпадает со временем жизни процесса. [Запуск](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/main.go#L19) · [Служба](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/deploy/vpnguard.service) · [Завершение](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/telemetry.go#L266)

## Сравнение вариантов

В A транзитом управляет отдельный агент. В B он выполняется внутри процесса-хоста. В C он сохраняет собственный жизненный цикл, а потребители разделяют только согласованные источники данных и контракты ресурсов. Оценки нагрузки и сложности качественные. Сравнительных измерений трёх реализаций пока нет.

| Критерий | A · Standalone | B · Embedded | C · Hybrid |
|---|---|---|---|
| Сложность реализации | Низкая для чтения локального состояния. Для сетевого клиента нужны защищённый транспорт, идентичность и версия контракта. | Высокая. Требуются импортируемое ядро, управление запуском и остановкой, владение горутинами и ресурсами. | Средняя при одном общем источнике. Возрастает при появлении нескольких процессов с правом записи. |
| Изменения существующего кода | Большинство модулей работает как сейчас. Для экспорта достаточно снимка и ограниченного адаптера. | Изменятся init, глобальные переменные, обработка сигналов, HTTP и запуск циклов. | Существующие реализации можно оставить поставщиками по умолчанию. Источник потоков и выход наблюдений заменяются по одному. |
| Накладные расходы | Сериализация и копирование при чтении API. Передавать агрегаты, измерять размер и частоту ответов. | Возможны дешёвые вызовы внутри процесса. Потребуются согласование доступа и копии изменяемых снимков. | Один сбор потока на узел уменьшает дублирование. Очередь и сериализация внешних событий добавляют задержку. |
| Отказоустойчивость | Потеря координатора изолируется от процесса агента. Остаются общие ОС, оборудование и канал. | Паника вне защищённого цикла или выход процесса затрагивают соседние модули. | Сбой внешнего классификатора должен переводить новые наблюдения в Unknown. Автономные правила и журнал остаются локальными. |
| Безопасность | Идентичность клиента, минимальные права, защищённый канал. Локальная доверенная сессия UI требует отдельного учёта при проксировании. | Модули разделяют память и привилегии. Go-интерфейс сам по себе не изолирует недоверенный код. | Поставщику классификации достаточно права публиковать наблюдения. Проверка полномочий на сетевое изменение остаётся у исполнителя. |
| Обновления | Агент и координатор обновляются раздельно. Для агента есть снимок версии и таймер отката. | Единый бинарник связывает выпуск и перезапуск нескольких ролей. | Версии контрактов согласуются на границе. При несовместимости отключается внешняя функция, автономные настройки сохраняются. |
| Общие ресурсы | Один агент пишет свои ресурсы. Соседний Firewall требует явного разделения таблиц, меток и очередей. | Общий процесс позволяет координировать доступ, но блокировки должны охватывать также внешнего помощника отката. | Общий контракт назначений, один писатель для каждого ресурса, локальный исполнитель и независимый откат. |
| Риск для соединений | Низкий при обновлении потребителя телеметрии. Перезапуск VPN, смена выхода или перезапись таблицы затрагивают транзит. | Перезапуск наблюдателя может повлечь перезапуск общего процесса. Для работающих сессий потребуется отдельная проверка. | Существенный риск при смене поставщика во время жизни потока. Сохранять закреплённый выход, сбрасывать недостоверную классификацию. |
| Постепенный переход | Сначала диагностика только на чтение, далее события, затем разрешённые задания. | Потребуется сначала отделить состояние и жизненный цикл в самостоятельном агенте, затем доказать безопасный запуск и выгрузку в хосте. | Внешние наблюдения сначала сравниваются с локальными в режиме чтения. Только после подтверждения эквивалентности можно оставить единственный источник. |

Основания для сравнения — состав ответа API, отмена и пределы поточного сборщика, сохранение маршрута через conntrack, независимое восстановление и обновление с резервной копией бинарника. ## Физическое размещение

| Размещение | Практический предел и критерий допуска |
|---|---|
| Один Linux-шлюз, только VpnGuard | Локальные UI, диагностика, DNS, маршрутизация и восстановление работают на узле. Проверить штатный запуск без внешнего сервера, перезагрузку и управление через реального клиента. Внешние услуги самого VPN и DNS имеют собственные условия доступности. [Запуск](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/main.go#L19) · [Автономный выбор выхода](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/routes.go#L87) |
| Тот же узел, VpnGuard и Firewall | Допустимы отдельные процессы на одной ОС. Оба воздействуют на то же ядро. Отдельные имена таблиц недостаточны для разрешения конфликтов порядка hooks, битов меток и NFQUEUE. До запуска второго писателя сверить назначения, проверить запрет Firewall на каждом выходе и сохранность чужих правил после отката. [Генерация цепочек](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/routes.go#L279) · [Восстановление снимка](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/route_snapshot.go#L109) |
| Traffic Node и отдельный сервер координатора/LLM | На узле остаются исполнитель, действующие политики, проверка прав, таймер и последнее принятое состояние. Через сеть передавать минимальные наблюдения и команды с ревизией и сроком. При разрыве связи диагностика и резервирование продолжаются локально. При восстановлении сверить состояние до выполнения накопленных заданий. [События смены выхода](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/routes.go#L432) · [Журнал и сроки](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/route_journal.go#L286) |
| Несколько узлов или совмещение нескольких ролей на устройстве | Идентичность потока и ресурс должны включать узел и сетевое пространство имён. Локальные epoch/generation и conntrack ID/zone значимы в своей области. При совмещении координатора, LLM и шлюза ограничить CPU и память аналитики и проверить задержку DNS и доступ к управлению под нагрузкой. Модулю, читающему готовый результат, отдельная VM не требуется. [Кадр потока](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/flow_events.go#L19) · [Привязка DPI](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/dpi_binding.go#L32) · [Локальный DNS](https://github.com/Fogiku/VpnGuard_linux/blob/cedd90c27ca10125ccfab48dd4a2022a36436f3d/dns_access.go#L208) |

**Когда менять вариант.** Для перехода A → C измерить, сколько ресурсов потребляет повторный сбор одних и тех же потоков и сколько стоит передача снимка. Проверить потерю провайдера, его обновление при живых TCP/UDP-сессиях, пропуски и предел памяти. Для перехода C → B дополнительно показать повторяемый Start/Stop в одном процессе, отсутствие оставшихся воркеров и слушателей, изоляцию ошибок и сохранность транзита при обновлении соседней роли. Сейчас только отдельная сессия событий имеет явные отмену и ожидание завершения.
