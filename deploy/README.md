# Развёртывание VpnGuard

## Установка на существующую Ubuntu

Из корня репозитория соберите агент командой `go build -o bin/vpnguard .`.
Сценарий `deploy/install.sh` устанавливает системные зависимости, включает маршрутизацию IPv4 и запускает службу VpnGuard через systemd.

## Тесты сценариев развёртывания

Из корня проекта:


```sh
python -m unittest discover -s deploy
```

## Выпуск обновления

В чистой копии исходников с тегом `vX.Y.Z`, соответствующим константе Version, выполните `python3 deploy/build_release.py /путь/к/копии-ветки-releases` с Python 3.9+ и Go. Команда собирает бинарники для Linux amd64 и arm64 и записывает манифест с их SHA‑256 и коммитом исходников. В репозитории сборок закоммитьте эти три файла и присвойте коммиту тег `bin-vX.Y.Z`. При публикации отправьте тег сборок и ветку `releases` одной командой `git push --atomic origin HEAD:releases bin-vX.Y.Z`. Исходный тег должен быть доступен на GitHub к моменту публикации.

Для выпусков начиная с 1.9.24 источником карточек панели служит корневой `CHANGELOG.md`. Добавьте в начало журнала раздел вида `## 1.9.27 — 22 ноября 2026` и маркированный список изменений. Проверка Go сверяет заглавную версию с константой агента, сборщик включает пункты этой версии в манифест.

### Совместная публикация

Из checkout нужного коммита после отправки своей ветки `release/*` можно выполнить одну команду (Python 3.10+, Go и Git с доступом к репозиторию):

```sh
python deploy/publish_release.py release/1.9.27 --publish
```

Без `--publish` команда выполняет проверку и пробную отправку. Она дожидается успешного Linux CI для точного SHA, собирает обе архитектуры во временной копии, сверяет манифест и SHA‑256 и отправляет обе ветки и оба тега одной транзакцией. Если другой исполнитель успел опубликовать несовместимое изменение, Git отклоняет отправку. Обновите свою ветку и при необходимости выберите следующий номер. Остальные checkout и настройки Git исполнителей сохраняются. Ручной способ выше также поддерживается.

### Устойчивость TCP при смене политики

На отдельном Linux-стенде с правами на создание сетевых пространств имён, установленными iproute2, nftables, util-linux, Python 3 и Go выполните из корня репозитория:

```sh
sudo unshare --net env VPNGUARD_NETNS_TEST=1 VPNGUARD_FLOW_LOAD=1 go test -count=1 -v -run '^TestTcpFlowPinningIsolatedKernel$' .
```

Клиент открывает четыре TCP-соединения через исходный выход и сверяет адрес, увиденный эхо-сервером, при каждом обмене. За 12 циклов тест 24 раза меняет маршрут для новых соединений. В журнале выводятся длительность и число подтверждённых обменов по каждому сокету. Затем отдельно проверяются новый поток, отказ выхода и восстановление соединения.

На том же стенде вместо `VPNGUARD_FLOW_LOAD=1` задайте `VPNGUARD_UDP_RECOVERY=1` для проверки UDP. Один сокет отправляет нумерованные пакеты до отказа VPN, при недоступном выходе и после его восстановления. При объявленном отказе VPN тест открывает новые сокеты с разными исходными портами. Без разрешённого резерва новый поток должен блокироваться. После выбора Direct резервом новый поток должен пройти через WAN, а закреплённый за VPN сокет должен остаться заблокированным. После восстановления новый поток должен снова пойти через VPN. Тест проверяет ответы сервера, адрес источника и счётчик пакетов на прямом выходе. Время первого ответа отсчитывается от начала соответствующей серии после применения политики.

Для длительной проверки добавьте к этому запуску `VPNGUARD_UDP_SOAK=1` и выделите тесту не менее четырёх минут (`go test -timeout 4m`). Сокет открывается на резервном Direct и продолжает обмен во время восстановления VPN. После подтверждения выхода нового сокета через VPN тест ещё 125 секунд проверяет у каждого ответа адрес Direct и номер пакета.

## Клиентская проверка воспроизведения

На проверяемом клиенте установите Python и Playwright (`python -m pip install playwright`). Для установленного Edge используйте команду ниже. Для Chromium из комплекта Playwright сначала выполните `python -m playwright install chromium` и уберите `--channel msedge`.

```sh
python deploy/probe_client_playback.py --channel msedge --video-id jNQXAC9IVRw --control https://example.org/ --path-label wg-zapret --runs 2
```

Укажите независимый контрольный URL с ожидаемым конечным ответом 2xx. Каждый замер открывает чистую браузерную сессию, запрашивает контрольную страницу и выбранный ролик. Успех требует пяти последовательных секунд продвижения времени видео с ростом счётчика кадров. Окно наблюдения после получения ответа страницы составляет 20 секунд. Страница согласия, ограничение региона, требование входа или длительная реклама могут оставить воспроизведение неподтверждённым.

JSON содержит время, оба HTTP-результата, длительность наблюдаемого воспроизведения и итог повторов. Метку пути задаёт оператор. Для сравнения разрешённых выходов повторите команду с тем же роликом и контролем на клиентах с известной политикой, сохраните отчёты и сверьте выход с данными шлюза. Вывод о причине блокировки требует независимого подтверждения.

Для проверки Discord Gateway используйте `--discord` отдельно или вместе с `--video-id`. В каждом замере браузер открывает WebSocket и ожидает до десяти секунд событие Hello с корректным интервалом heartbeat. Поле `discord_gateway` описывает этот обмен. Голос требует отдельного двустороннего испытания.

Состояние этапов, порядок реализации и критерии выпуска приведены в [плане 2.0](../ROADMAP_2_0.md).

## Сопоставление контрольного соединения с записью шлюза

С проверяемого WG- или LAN-клиента выполните команду с именем доступного HTTPS-хоста и настроенным SSH-псевдонимом шлюза. Потребуются Python 3, OpenSSH и уже известный SSH-ключ хоста. На шлюзе требуется право чтения conntrack; для настроенного беспарольного sudo добавьте `--sudo`.

```sh
python deploy/probe_client_path.py --gateway vpnguard --host example.org
```

Клиент держит проверенное TLS-соединение открытым, пока шлюз ищет совпадение в IPv4 conntrack по протоколу, двум адресам и портам. Затем клиент запрашивает HTTP-заголовки по тому же сокету. Шлюз возвращает только результат сопоставления. При нескольких зонах, неполном снимке, NAT перед шлюзом или недоступности наблюдения возможны соответственно ambiguous, incomplete, missing или gateway_unavailable. Код закрепления находится в битах 16–23. Панель «Потоки» расшифровывает фиксированные назначения и показывает код дополнительных VPN.

Хеш относится к выводу `nft -s -n list table inet vpnguard` при двух чтениях вокруг снимка. В него не входят системные ip rule, таблицы маршрутов и настройки провайдера. Это свидетельство о контрольном TCP-сокете; путь видео, голоса и фактический физический интерфейс требуют собственных наблюдений.

Начиная с 1.9.28 поле `policyRevision` содержит SHA-256 скомпилированной конфигурации nftables и запланированных команд маршрутизации. Маркер появляется при применении правил. Значение относится к моменту наблюдения сокета. Фактическое состояние таблиц ip и ревизия в момент создания соединения требуют отдельного измерения. Поле `pinnedExit` расшифровывает фиксированную метку conntrack. Для динамического выхода сохраняется исходный `pinByte`.

Значение `correlation=pin_and_observed_policy` означает, что найден один поток с известным закреплением, а шлюз прочитал одинаковую таблицу с ревизией до и после снимка. Для старой таблицы вернётся `unversioned_table`, для нулевой или неизвестной метки — `unpinned` или `unknown_pin`. При смене или недоступности таблицы ревизия пуста.

### Привязка Discord Gateway к выходу

На проверяемом клиенте установите `websockets==16.0` в виртуальное окружение Python. Запустите `python deploy/probe_client_path.py --gateway vpnguard --discord`. При необходимости добавьте `--sudo`. Проба открывает IPv4 WebSocket к gateway.discord.gg с проверкой сертификата, получает Hello и читает conntrack по адресам и портам этого же открытого сокета. Вход в учётную запись Discord не требуется.

`discord_gateway=hello` подтверждает сигнализацию. При `flow.correlation=pin_and_observed_policy` поля `pinnedExit` и `policyRevision` указывают закреплённый выход и наблюдаемую ревизию. Если шлюз недоступен по SSH, успешный Hello сохраняется, а путь остаётся неподтверждённым. Физический интерфейс передачи и двусторонний голос требуют отдельных измерений.

## Попарное сравнение испытательных профилей

На одном испытательном Linux-хосте подготовьте два сетевых пространства с разрешёнными выходами и нужными профилями. Установите Playwright и Chromium для обычного пользователя. Пример для Bash запускает одинаковые пробы одновременно. Подставьте пути к файлам двух испытательных профилей вместо `/path/to/base.conf` и `/path/to/candidate.conf`. При работе из виртуального окружения `command -v python3` должен указывать на его интерпретатор.

```bash
(
  set -eu
  session="lab-$(date -u +%Y%m%dT%H%M%SZ)"
  mkdir "$session"
  probe=( "$(command -v python3)" "$PWD/deploy/probe_client_playback.py"
          --lab-session "$session" --video-id jNQXAC9IVRw --discord
          --control https://example.org/ --runs 3 )
  sudo -v
  sudo -n ip netns exec vg-base sudo -H -u "$(id -un)" -- "${probe[@]}" \
    --path-label vg-base --profile-file /path/to/base.conf > "$session/base.json" &
  base_pid=$!
  sudo -n ip netns exec vg-candidate sudo -H -u "$(id -un)" -- "${probe[@]}" \
    --path-label vg-candidate --profile-file /path/to/candidate.conf > "$session/candidate.json" &
  candidate_pid=$!
  wait "$base_pid"
  wait "$candidate_pid"
  python3 deploy/compare_client_profiles.py "$session/base.json" "$session/candidate.json"
)
```

В режиме файловых ревизий передайте `--profile-file /path/to/profile.conf` вместо `--profile-revision` с обеих сторон. Укажите файл с полным содержимым испытательного профиля. Клиент вычисляет SHA-256 до и после серии. Если значения отличаются, отчёт не записывается. Хеш охватывает только байты указанного файла. Соответствие работающего экземпляра этому профилю проверяет оператор.

Сравнение файловых отчётов выводит `profiles` с двумя SHA-256 и `target_set_sha256` для состава проб, видео, контрольной цели и рефлекторов. История рекомендаций учитывает оба хеша профилей, набор целей и ожидаемые сети выхода. Ранее сохранённые отчёты с ручными ревизиями по-прежнему можно сравнивать между собой.

Сравнение принимает 2–5 повторов при одинаковых целях, версии и канале браузера. Начало двух замеров в паре может различаться максимум на 120 секунд. Для каждого приложения результат указывает, где функция наблюдалась во всех повторах. Сбой независимого HTTPS-контроля, прерванное наблюдение и смешанные исходы дают `inconclusive`. Контрольный адрес хранится в виде SHA-256. Идентификаторы ядра и пространства привязывают наблюдение к месту запуска браузера. Соответствие выбранного профиля фактическому сетевому выходу проверяет оператор.

## Адрес выхода IPv4/IPv6 и медиасоединения YouTube

Для проверки выхода добавьте к команде `probe_client_playback.py` один или оба параметра ниже. Замените адреса серверов и сети из примера своими. Для двух профилей сравнения используйте одни и те же контрольные URL и задайте ожидаемую сеть каждого профиля отдельно.

```text
--egress-v4 https://v4.example.org/ip 192.0.2.0/24
--egress-v6 https://v6.example.org/ip 2001:db8::/48
```

Нужны доступные браузеру HTTPS-серверы с действительным сертификатом, желательно с отдельными A и AAAA именами. Каждый возвращает без перенаправления JSON вида `{"ip":"192.0.2.7"}` с типом `application/json`. Адрес должен определяться по входящему соединению доверенным сервером. Используйте ответ с `Cache-Control: no-store`. Браузер обращается к серверу после пробы приложения. В JSON сохраняются полученный IP, ожидаемая сеть, хеш URL и результат. Значения `outside_expected`, `wrong_family` и `unavailable` обозначают соответственно выход за пределы сети, другое семейство и отсутствие достоверного ответа. При любом из этих исходов попарное сравнение сохраняет наблюдения приложения и даёт общий итог `inconclusive`. Без параметров обращения к этим серверам отключены.

В `media_network.peers` Chromium записывает до 16 уникальных сочетаний адреса, порта и протокола удалённой стороны для успешных HTTPS-ответов audio/video на пути `/videoplayback` поддоменов googlevideo.com. Там могут встречаться прокси и CDN. Пустой список означает отсутствие подходящего наблюдения. Идентификаторы ролика в URL медиазапросов, параметры ссылок и содержимое пакетов в этот список не попадают. Полный клиентский отчёт с включённой проверкой выхода содержит видимые серверу адреса клиента.

### История испытаний и рекомендация профиля

В команде сравнения первый файл соответствует базовому профилю, второй — кандидату. Сохраняйте этот порядок и используйте устойчивую метку сети для повторных сессий:

```sh
python3 deploy/compare_client_profiles.py base.json candidate.json --history trials.sqlite --network office-wg
```

В JSON раздел `shadow` показывает для каждого сервиса до восьми последних результатов и поле `suggested_profile`. Для рекомендации требуются два последних согласованных испытания за 24 часа с одинаковым победителем. Начало следующей серии должно отстоять от последнего замера предыдущей минимум на 120 секунд. Сравниваются одинаковые сеть, профили, браузер, контрольная цель, параметры проверки внешнего адреса и, для YouTube, ролик. Проверка внешнего адреса подтверждает путь к контрольному серверу. Статус медиапути и работа голоса оцениваются отдельно.

При равенстве, расхождении, недостатке свежих наблюдений или отсутствии проверки выхода рекомендация пуста; причина указана в `reason`. Имя сессии должно быть уникальным для нового испытания. Повторная обработка тех же данных идемпотентна. Попытка заменить результат уже записанной сессии в том же контексте завершается ошибкой. База хранит компактные итоги и хеши, до 4096 записей; при успешном импорте удаляются записи старше 30 дней. Профиль на шлюзе выбирает оператор.
