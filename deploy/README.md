# Развёртывание VpnGuard

## Установка на существующую Ubuntu

Из корня репозитория соберите агент командой `go build -o bin/vpnguard .`.
Сценарий `deploy/install.sh` устанавливает системные зависимости, включает маршрутизацию IPv4 и запускает службу VpnGuard через systemd.

## Тесты сценариев развёртывания

Из корня проекта:


```sh
python -m unittest discover -s deploy
```

## Выпуск обновления

В чистой копии исходников с тегом `vX.Y.Z`, соответствующим константе Version, выполните `python3 deploy/build_release.py /путь/к/копии-ветки-releases` с Python 3.9+ и Go. Команда собирает бинарники для Linux amd64 и arm64 и записывает манифест с их SHA‑256 и коммитом исходников. В репозитории сборок закоммитьте эти три файла и присвойте коммиту тег `bin-vX.Y.Z`. При публикации отправьте тег сборок и ветку `releases` одной командой `git push --atomic origin HEAD:releases bin-vX.Y.Z`. Исходный тег должен быть доступен на GitHub к моменту публикации.

### Устойчивость TCP при смене политики

На отдельном Linux-стенде с правами на создание сетевых пространств имён, установленными iproute2, nftables, util-linux, Python 3 и Go выполните из корня репозитория:

```sh
sudo unshare --net env VPNGUARD_NETNS_TEST=1 VPNGUARD_FLOW_LOAD=1 go test -count=1 -v -run '^TestTcpFlowPinningIsolatedKernel$' .
```

Клиент открывает четыре TCP-соединения через исходный выход и сверяет адрес, увиденный эхо-сервером, при каждом обмене. За 12 циклов тест 24 раза меняет маршрут для новых соединений. В журнале выводятся длительность и число подтверждённых обменов по каждому сокету. Затем отдельно проверяются новый поток, отказ выхода и восстановление соединения.

На том же стенде вместо `VPNGUARD_FLOW_LOAD=1` задайте `VPNGUARD_UDP_RECOVERY=1` для проверки UDP. Один сокет отправляет нумерованные пакеты до отказа VPN, при недоступном выходе и после его восстановления. При объявленном отказе VPN тест открывает новые сокеты с разными исходными портами. Без разрешённого резерва новый поток должен блокироваться. После выбора Direct резервом новый поток должен пройти через WAN, а закреплённый за VPN сокет должен остаться заблокированным. После восстановления новый поток должен снова пойти через VPN. Тест проверяет ответы сервера, адрес источника и счётчик пакетов на прямом выходе. Время первого ответа отсчитывается от начала соответствующей серии после применения политики.

Для длительной проверки добавьте к этому запуску `VPNGUARD_UDP_SOAK=1` и выделите тесту не менее четырёх минут (`go test -timeout 4m`). Сокет открывается на резервном Direct и продолжает обмен во время восстановления VPN. После подтверждения выхода нового сокета через VPN тест ещё 125 секунд проверяет у каждого ответа адрес Direct и номер пакета.

## Клиентская проверка воспроизведения

На проверяемом клиенте установите Python и Playwright (`python -m pip install playwright`). Для установленного Edge используйте команду ниже. Для Chromium из комплекта Playwright сначала выполните `python -m playwright install chromium` и уберите `--channel msedge`.

```sh
python deploy/probe_client_playback.py --channel msedge --video-id jNQXAC9IVRw --control https://example.org/ --path-label wg-zapret --runs 2
```

Укажите независимый контрольный URL с ожидаемым конечным ответом 2xx. Каждый замер открывает чистую браузерную сессию, запрашивает контрольную страницу и выбранный ролик. Успех требует пяти последовательных секунд продвижения времени видео с ростом счётчика кадров. Окно наблюдения после получения ответа страницы составляет 20 секунд. Страница согласия, ограничение региона, требование входа или длительная реклама могут оставить воспроизведение неподтверждённым.

JSON содержит время, оба HTTP-результата, длительность наблюдаемого воспроизведения и итог повторов. Метку пути задаёт оператор. Для сравнения разрешённых выходов повторите команду с тем же роликом и контролем на клиентах с известной политикой, сохраните отчёты и сверьте выход с данными шлюза. Вывод о причине блокировки требует независимого подтверждения.

Для проверки Discord Gateway используйте `--discord` отдельно или вместе с `--video-id`. В каждом замере браузер открывает WebSocket и ожидает до десяти секунд событие Hello с корректным интервалом heartbeat. Поле `discord_gateway` описывает этот обмен. Голос требует отдельного двустороннего испытания.
