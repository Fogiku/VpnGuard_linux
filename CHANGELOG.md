# Журнал обновлений VpnGuard для Linux

Нумерация Linux начинается с 1.0 и не связана с прежней 4.0.0-stage1. Каждая новая установленная версия получает следующий номер; повторная установка того же бинарника сохраняет номер и создаёт отдельное событие установки. Результаты установки хранятся на шлюзе в /var/lib/vpnguard/updates.json и доступны на странице «Обновления».

## 1.9.40 — 23 ноября 2026

- Страница olcRTC-Server показывает текущий этап установки, прошедшее время и результат. Ошибки с указанием этапа и сообщением установщика доступны в веб-журнале.

## 1.9.39 — 23 ноября 2026

## 1.9.38 — 23 ноября 2026

- При добавлении устройства можно указать HTTPS-адрес сервера Jitsi. Панель сгенерирует отдельное имя комнаты.

При сверке адреса с правилом можно указать IPv4 источника DNS-запроса и проверить последний полный A-ответ по этому имени и остаток TTL. Если DNS пересылает роутер, виден его адрес. В памяти сохраняются до 64 источников и четырёх имён правил на источник.

## 1.7 — 17 ноября 2026

- Добавлены клиентские DNS-входы: `dns.serveWG` включает UDP/TCP 53 на адресе WG-сервера; `dns.lanAddress` задаёт отдельный частный адрес этого ПК, `dns.allowLAN` — до 16 частных IPv4-подсетей. По умолчанию клиентские входы выключены, включение фиксируется отдельно в настройках поставки.
- Каждый вход привязан к своему адресу и Linux-интерфейсу через SO_BINDTODEVICE. WG принимает адреса своей /24-подсети через WG-интерфейс (peer и AllowedIPs проверяет WireGuard). LAN принимает только заданные подсети. Wildcard/public bind, публичные CIDR, IPv6 ACL и петли upstream к собственным DNS-входам отклоняются.
- ACL проверяется для каждого UDP-пакета и каждого сообщения в TCP-соединении, включая повторную проверку перед отправкой ответа. Отзыв доступа действует на открытые соединения; отказ не вызывает запрос к upstream. Сохранены ограничения размера и параллелизма.
- Новые сокеты подготавливаются с запретом запросов; настройки сохраняются перед включением ACL. Ошибка привязки или записи оставляет прежние входы доступными. API `dnsService` и таблица на вкладке DNS показывают адреса, интерфейсы и готовность. В симуляции внешние DNS-сокеты не открываются.
- Действие «DNS шлюза в экспортируемых WG-профилях» меняет только `wg.dns`; ключи, пиры и конфигурация сервера не меняются. Уже импортированные профили не получают DNS через протокол WireGuard: обновите строку DNS или импортируйте профиль заново.
- Установщик проверяет объявленные DNS-настройки и готовность нужных входов при подтверждении; откат восстанавливает исходный config.json вместе с прежней версией. Добавлен сетевой пробник DNS, в том числе из временного реального WG-клиента.
- IPv6-политика: DNS-входы только IPv4, AAAA возвращает REFUSED. Системный IPv6 и IPv6-трафик клиентов не блокируются и не маршрутизируются этим компонентом; HTTPS/SVCB и DoH/DoT не дают гарантии обхода IPv6 только посредством DNS.

## 1.6 — 17 ноября 2026

- Добавлен DNS-компонент: UDP/TCP на 127.0.0.1:5353 (15353 в симуляции), upstream по умолчанию 127.0.0.53:53. Используется существующий systemd-resolved с настройками MeduzaVPN/провайдера. Системный resolver, DHCP и DNS клиентских профилей не меняются. Новая вкладка содержит настройки, диагностический запрос и TTL-кэш.
- Разрешение доменов правил использует ограниченный кэш: до 256 корневых доменов, 512 наблюдаемых имён и 64 IPv4 на имя. A учитываются только из answer по цепочке CNAME от вопроса; effective TTL ограничен TTL A/CNAME и часом. Старые ответы CDN сохраняются до своего срока. Glue/additional и TTL=0 не добавляются в маршрутизацию. Кэш в памяти, после рестарта адреса запрашиваются заново.
- Сроки проверяются каждые пять секунд; фоновые изменения проходят через существующую транзакцию маршрутов. При ожидающем подтверждении они откладываются. Для наблюдаемого домена новый ответ прокси отправляется после согласования правил; ошибка применения даёт SERVFAIL. Изменения адресов воздействуют на новые потоки при включённом закреплении.
- DNS-обновление не переписывает неизменившиеся ip rule/default-маршруты. Если домен не разрешён, правило «домен + порт» пропускается, не превращаясь в правило на все подключения этого порта.
- Проверяются ID и вопрос ответа; усечение UDP вызывает TCP-повтор. Прокси ограничивает параллелизм и размеры, крупные UDP-ответы отдаются с TC для TCP-повтора. Парсер DNS взят из официального Go 1.24.9 с исходной BSD-лицензией, без новых модульных зависимостей. Самостоятельной DNSSEC-валидации нет.
- Политика IPv6 этого компонента: AAAA возвращает REFUSED, IPv6-адреса не включаются в IPv4-правила. Это не системная блокировка IPv6; HTTPS/SVCB и отдельные DoH/DoT клиентов не дают гарантии IPv4-маршрутизации. Прокси доступен только локально, подключение клиентов WG/LAN и проверка IPv6 остаются следующим шагом.

## 1.5 — 17 ноября 2026

- Начата сетевая телеметрия: чтение анонимных счётчиков правил `inet vpnguard / classify` раз в 10 секунд, агрегация вариантов портов по ID правила, подписи профилей/клиентских переопределений. Чтение не обнуляет счётчики и не меняет nftables. До 256 строк в таблице, отсутствие правила показано прочерком.
- Измеряется WAN и каждый активный VPN с отдельной таблицей: пять ICMP-запросов к одному IPv4-адресу примерно раз в 30 секунд с привязкой к интерфейсу и ограничением времени. Средний RTT берётся из статистики ping; ΔRTT — среднее абсолютное изменение RTT соседних полученных пакетов, без пар через пропуски. Это не mdev и не измерение задержки приложений.
- Считаются ICMP-потери по полной серии из пяти пакетов. Ошибка запуска/прав/таймаут с неполной статистикой не превращаются в 100% потерь. Фильтрация ICMP не меняет здоровье модулей и не вызывает действия восстановления.
- Контрольный IPv4 (`net.qualityIP`, по умолчанию 1.1.1.1) и включение (`net.qualityEnabled`) доступны в диагностике. Новые метрики записываются в существующий checkpoint с теми же лимитами. Данные качества старше 45 с и счётчиков старше 20 с не копируются как текущие; после изменения ядра старое поколение счётчиков исключается из истории.
- Мониторинг сохраняет раскрытие таблицы при новых данных и выделение текста. Счётчики классификации не показывают полный трафик закреплённых соединений: они обходят классификацию; при применении правил счётчики могут сбрасываться. DNS не перенастраивался.

## 1.4 — 17 ноября 2026

- Начат этап постоянной телеметрии: `telemetry.json` хранит до часа метрик с шагом 5 секунд и 200 последних решений. Решения содержат полную дату. Сбор не меняет маршруты, DNS и службы VPN.

- Файл ограничен 4 МиБ, временная копия при записи требует ещё до 4 МиБ. При достижении лимита удаляются старые измерения, при смене клиентов API ограничивает число рядов. Повреждённая история не блокирует запуск; сбор продолжается в памяти, состояние записи видно в мониторинге.
- Пропуски времени и исчезнувшие метрики передаются как null. Графики не соединяют разрывы; доступность считает только измеренные состояния. Во время выделения текста фоновые ответы мониторинга не перерисовывают страницу.

## 1.2 — 16 ноября 2026

- В «Обновления» добавлен прогресс разработки по девяти этапам плана. Для каждого этапа показаны выполненные пункты, оставшиеся задачи и область проверок; полосы отражают чек-листы.
- Журнал сетевой транзакции сохраняется и синхронизируется на диск до изменения настроек и ядра. Межпроцессная блокировка защищает работу агента и отдельного восстановления.
- Для изменений маршрутов, сетевых параметров и ручного отката взводится независимый таймер systemd. При незавершённой операции возвращаются собственные nftables/ip rule/default-маршруты, profiles/routes.json и только сетевые ключи config.json.

- Веб автоматически подтверждает связь отдельным запросом с исходного адреса. Без подтверждения за 90 секунд выполняется восстановление. Старой странице предлагается обновиться до изменения политик.
- API записи маршрутов требует X-VG-Route-Confirm: 1. После записи клиент получает ID из routes.pending и отправляет POST /api/routeconfirm с тем же адресом и JSON {"id":"…"}; нужны обычная авторизация и X-VG. Чтение API не меняется.
- Диагностика показывает последние 50 операций маршрутизации (на странице — 10 последних). Снимки и история имеют закрытые права доступа.
- Переименование профиля или правила не меняет ядро. Настройки и профиль последнего отката сохранены на диске.
- Откат версии программы отменяет/архивирует незавершённую сетевую операцию кандидата под той же блокировкой, чтобы два восстановления не мешали друг другу.

Границы: автоматические изменения подтверждаются после успешного выполнения команд; отдельный запрос проверяет связь управления при ручных изменениях из веба/API. Эта защита не заменяет прикладные проверки всех клиентов и не охватывает отдельные операции перенастройки самих VPN-служб. Тесты отказа ядра выполняются в изолированной сети.
