# VpnGuard для Linux

VpnGuard — агент для Ubuntu Server LTS с веб-интерфейсом управления VPN, маршрутизацией и диагностикой шлюза. Текущая версия агента — 1.9.20.

Аудит базовой версии 1.9 и этапы перехода к 2.0 описаны в [программе развития](PLATFORM_INTEGRATION_READINESS.md).

Порядок выбора задачи и передачи работы между исполнителями описан в [AGENTS.md](AGENTS.md).

## Сборка и запуск в режиме имитации

Требуется Go 1.22 или новее. Из корня репозитория выполните:

```sh
go test ./...
go build -o bin/vpnguard .
./bin/vpnguard --sim
```

Откройте http://127.0.0.1:8766/. В режиме имитации агент использует виртуальные службы и записывает состояние в `data-sim/`.

Для Windows запустите `go build -o bin/vpnguard.exe .`, затем `run-sim.cmd`.

## Обновление из приложения

Во вкладке **Обновления** нажмите **Проверить обновления**, затем **Установить**. Шлюз сверяет версию и SHA‑256 готовой сборки для своей архитектуры. После перезапуска снова откройте эту вкладку с того же компьютера и нажмите **Проверить связь и подтвердить**. Без подтверждения за четыре минуты штатный таймер запускает откат. Для установки нужен штатный Linux-шлюз с systemd, работающим MeduzaVPN и WG-Server. В симуляторе доступна проверка версии.

## Обновление шлюза из Windows

Скачайте [Update-VpnGuard.ps1](https://github.com/Fogiku/VpnGuard_linux/raw/refs/heads/main/web/Update-VpnGuard.ps1) на компьютер с Windows. Начиная с версии 1.9.2 этот файл также доступен во вкладке **Обновления** на шлюзе.

На компьютере нужны PowerShell 5.1 или новее и клиент Windows OpenSSH (`ssh` и `scp`). Компьютер скачивает опубликованный Linux-бинарник для x86‑64 или ARM64 и сверяет SHA‑256. Шлюзу нужны доступ по SSH, Python 3, systemd и права администратора через `sudo -n`. Штатная проверка обновления рассчитана на работающий VpnGuard с подключённым MeduzaVPN и WG-Server. Завершите ожидающие подтверждения изменения маршрутов до обновления.

При первом подключении сверьте отпечаток SSH-ключа шлюза и сохраните его в known_hosts штатным клиентом SSH. Откройте PowerShell в папке со скриптом и замените `gateway.example` адресом или именем вашего шлюза:

```powershell
.\Update-VpnGuard.ps1 -Gateway gateway.example -User vpnadmin
```

Если Windows пометила скачанный файл как заблокированный, проверьте его содержимое и выполните `Unblock-File .\Update-VpnGuard.ps1`. Для нестандартного SSH-порта или отдельного ключа добавьте `-Port 2222` или `-IdentityFile "$env:USERPROFILE\.ssh\id_ed25519"`.

По умолчанию скрипт берёт последний выпуск из манифеста ветки `releases`. Для конкретной версии укажите, например, `-Version 1.9.2`. Перед заменой агента установщик сверяет SHA‑256 переданного бинарника и версию, сохраняет прежний бинарник, конфигурацию и состояние сети и ставит таймер отката на четыре минуты. Подтверждение приходит через новое SSH-соединение после проверки API, процессов туннелей, состояния WG, служб и HTTPS через VPN. Если подтверждение не дошло, результат можно посмотреть во вкладке **Обновления → История установки** после срабатывания таймера.

## Отчёт для передачи в чат

Откройте **Диагностика → Проверить сейчас**, дождитесь результатов и нажмите **Скачать отчёт проверки**. Приложите полученный файл TXT к сообщению. В нём указаны версия, режим агента, итог последнего обновления и результаты каждой показанной проверки. Для zapret.sites отчёт содержит результаты по целям или причину остановки до первого запроса. Пользовательские URL обозначаются порядковыми номерами. Свободный текст системных команд, журналы, конфигурации клиентов и поля доступа в выгрузку не входят.

## Модули

Модуль — один файл `mod_*.go`, который реализует интерфейс `Module` и регистрируется в `init()`.
Он сам описывает свою веб-страницу: поля настроек, действия, таблицы и проверки. Поэтому новый модуль
появляется в меню, в диагностике, в мониторинге и в списке выходов без правок интерфейса и ядра.

Каждый модуль работает в своём потоке со своим ритмом. Модуль, у которого есть `Exit()`, становится
узлом-выходом в редакторе маршрутов.

### Дополнительные выходы WireGuard

Если на шлюзе уже настроен отдельный исходящий туннель WireGuard, откройте **Диагностика → Интернет** и заполните поле **Дополнительные выходы WireGuard**. Например, значение `wg1,wg2` подключает два выхода. Сохраните поле и перезапустите службу командой `sudo systemctl restart vpnguard`. Для локальной настройки то же значение хранится под ключом `vpn.extraWireGuard` в `/var/lib/vpnguard/config.json`. Настройками пиров и запуском этих туннелей управляет администратор. Для полного IPv4-выхода пир должен принимать нужные адреса назначения. При использовании wg-quick параметр `Table = off` оставляет установку маршрутов агенту.

Во вкладке **Маршруты** видны назначенные метки, таблицы и приоритеты. Выход можно выбрать в правиле профиля или в качестве резерва. Агент проверяет наличие пира и доступность контрольного адреса через интерфейс. Один интерфейс должен принадлежать одному выходу. Входящий WG-Server и интерфейс провайдера имеют отдельные роли.

Автоматические назначения привязаны к ID экземпляра и хранятся в `route-assignments.json` в каталоге данных. Сохраняйте этот файл вместе с резервной копией конфигурации. Если временно убрать интерфейс из списка, его номера остаются зарезервированными. При включённом закреплении потоков такие соединения блокируются до возврата выхода. Модуль нового туннеля может запросить такое же назначение через `Exit{Iface: имя, AutoRoutes: true}`.

## Маршруты: как это устроено

- Клиент WG-Server входит в профиль. У профиля список правил, они проверяются сверху вниз.
- У клиента могут быть свои правила: они стоят выше правил профиля.
- Правило: условие (готовый набор, домены, адреса, сети, порты) и выход.
- У выхода есть резерв и действие, если не работает ни он, ни резерв: блокировать или пустить напрямую.
- `routes.go` собирает из этого один сценарий nftables. Пакеты клиентов получают метку выхода,
  `ip rule` отправляет метку в таблицу маршрутов нужного туннеля, метка zapret уходит в очередь nfqws2.
- Сценарий применяется целиком одной операцией. Если nft его отклонил, остаются прежние правила.
- Синтаксис сценария проверен командой `nft -c` (nftables 1.0.9); правило с очередью в песочнице
  не проверилось, потому что в её ядре нет модуля очередей.

Домены превращаются в адреса через DNS раз в 10 минут. Для сайтов с часто меняющимися адресами этого мало:
на следующем этапе нужен DNS шлюза, который пополняет наборы адресов сам.

## WG-Server

Вкладка начинается с настроек: **Сервер** (подсеть, UDP-порт, MTU) и **Для клиентов** (внешний адрес с портом,
DNS, AllowedIPs, keepalive). Перед каждым изменением сервера делается резервная копия (`data/wg-backup`, последние 30),
любую можно восстановить из таблицы на той же вкладке. Кнопки: конфигурация сервера (ключи скрыты), правка
конфигурации целиком — файл проверяется построчно, ошибка называет строку, форма при ошибке не закрывается;
смена ключа сервера; создание сервера заново (подтверждение словом ЗАНОВО); починка службы (файл заново,
автозапуск, перезапуск). У клиента — QR и конфигурация с кнопками «Скопировать» и «Скачать .conf».
При смене подсети клиенты переезжают с тем же последним числом, их профили и свои правила в «Маршрутах» — за ними.
В состоянии видно: служба и автозапуск, какой порт слушает интерфейс, совпадает ли файл с настройками VpnGuard.

DNS для клиентов по умолчанию — 1.1.1.1: своего DNS на шлюзе пока нет (этап 3).

## Вкладка «Интернет»

Убрана из меню. Состояние провайдера — строкой на главной, системные проверки (пересылка пакетов, время, диск)
и настройки (интерфейс провайдера, адрес проверки) — на вкладке «Диагностика». Модуль `inet` остаётся
источником состояния для остальных модулей.

## Снимок для внешней аналитики (этап 7.1)

При включённой удалённой диагностике запрос `GET /v1/diagnostics/snapshot` использует заголовок `X-Token`, действующий срок доступа и разрешённую сеть. Для передачи внешнему аналитику предназначено тело ответа. Токен предоставляет доступ и к другим диагностическим отчётам.

JSON содержит версию схемы и агента, признаки симуляции и готовности маршрутизации. В массиве modules до десяти встроенных модулей с полями id, level (−1 выключен, 0 норма, 1 предупреждение, 2 сбой) и up. Объект decisions содержит числа записей info, warning, error и other в текущем журнале до 200 решений.

В панели «Диагностика» блок «Объяснение состояния» читает тот же снимок. Для внешнего клиента доступен `GET /v1/diagnostics/explanation` с тем же заголовком и ограничениями доступа. Ответ содержит schemaVersion, simulation, summary и observations. Локальный анализатор указывает модули с предупреждением или сбоем и значения level и up. Счётчики журнала описывают историю. Для установления причины требуются дополнительные проверки.

### Снимок соединений для контроллера (этап 7.3)

`GET /v1/diagnostics/flows` с заголовком `X-Token` возвращает, например, `{"schemaVersion":1,"snapshot":{"at":1795280000,"tcp":12,"udp":4,"truncated":false}}`. Поле `at` содержит время сбора в секундах Unix. Счётчики относятся к строкам последнего снимка IPv4. При `truncated: true` сбор достиг лимита, и фактическое число соединений может быть больше. При успешном пустом снимке оба счётчика равны нулю. До первого снимка, в имитации, после отключения сбора или ошибки чтения ответ содержит `"snapshot":null`. Запрос читает память агента. Сбор включается на странице «Потоки».

### Качество путей за пять минут

В разделе мониторинга и скачиваемом отчёте показаны ICMP-серии по WAN, MeduzaVPN и AWG. Поле `lastAt` указывает время последней попытки. Потери рассчитываются по сумме отправленных пакетов и ответов в завершённых сериях. Серии без полной статистики учитываются отдельно (`incomplete`). Максимумы среднего RTT и среднего изменения RTT по соседним ответам выражены в миллисекундах. Отсутствующее измерение обозначено прочерком, в JSON — `null`.

`GET /v1/diagnostics/link-quality` с действующим `X-Token` возвращает схему 1, включительные границы окна `from` и `through` в секундах Unix и массив `paths`. Ответ содержит только агрегаты для фиксированных идентификаторов `direct`, `meduza`, `awg`. Путь без измерений пропускается. В памяти хранятся до 16 последних серий на путь. При смене адреса цели или интерфейса первая новая серия начинает окно этого пути заново. Перезапуск агента или отключение ICMP-сбора очищает сводку при следующем проходе сборщика.

### События соединений IPv4

На странице «Потоки» включите сбор снимков и наблюдение жизненного цикла. Панель и `GET /v1/diagnostics/flow-lifecycle` показывают события с начала текущей подписки. Для API действует тот же диагностический токен. В ответе схемы 1 объект `observation` содержит идентификатор периода `epoch`, время получения последней сводки `at` (Unix), число наблюдаемых поколений `active`, число событий NEW `opened` и число пар NEW–DESTROY `completed`. Сюда попадают и соединения, завершившиеся между двумя снимками. Повторный NEW с тем же ключом начинает новое поколение.

`unmatchedUpdates` и `unmatchedDestroys` считают сообщения с известным conntrack ID без соответствующего NEW в этой подписке. Это возможно для соединений, существовавших до запуска наблюдателя. При отсутствии свежей сводки `observation` равен `null`. После перезапуска наблюдателя меняется `epoch`, и счётчики начинаются с нуля. Сравнивайте значения только в пределах одного периода. Кнопка «Скачать отчёт проверки» на странице диагностики включает время измерения и эти счётчики.

### История DNS и MeduzaVPN (этап 7.3)

`GET /v1/diagnostics/telemetry` использует тот же диагностический токен и ограничения доступа, что и журнал событий. Схема 1 возвращает `from` и `through` (включительные границы в секундах Unix), `stepSeconds` (5) и до 60 записей `samples` за последние пять минут. Каждая запись содержит время `at` и объект `values`. Пропуск времени или поля означает отсутствие измерения. Пустая история возвращается как `[]`.

Доступны накопительные счётчики `dns.queries`, `dns.errors`, `dns.refused`, размер кеша `dns.cache_entries` и уровни состояния модулей `dns.level`, `meduza.level`. Счётчики могут начинаться заново при перезапуске. Значения берутся из локальной истории агента.

### События контроллера (этап 7.3)

`GET /v1/diagnostics/events` использует тот же `X-Token` и ограничения доступа, что и снимок. Для соединения вне доверенной сети используйте SSH-туннель или HTTPS-прокси. Первый ответ содержит `reset: true`, обезличенный `snapshot` и непрозрачный `cursor`. Примените снимок и сохраните курсор. Для следующего опроса передайте его в `?cursor=...`. Каждый читатель хранит свой курсор.

При `reset: false` массив `events` содержит уведомления после курсора в порядке `sequence`. Типы: `inet.lost`, `inet.restored`, `exit.changed`, `routes.changed`. Поле `module` выдаётся для известных встроенных модулей. Уведомление служит поводом перечитать нужное состояние. Сохраняйте новый курсор после обработки всего ответа. Пустой массив означает отсутствие новых уведомлений. Агент хранит 128 событий в памяти. При отставании, неверном курсоре или перезапуске замените локальное состояние возвращённым снимком. Изменения во время сборки снимка могут повторно отразиться в следующем опросе.

### Подключение провайдера рекомендаций

Для подключения собственного адаптера задайте в окружении процесса `VPNGUARD_DIAGNOSTIC_PROVIDER=http://127.0.0.1:9091/review`. Порт и путь выбирает оператор. После запуска с этой переменной в диагностике появится кнопка «Запросить рекомендацию». Пустое значение выключает подключение. Адрес должен содержать числовой loopback-IP.

По нажатию кнопки API панели `POST /api/diag/recommendation` отправляет адаптеру JSON-снимок v1 методом POST. Адаптер возвращает HTTP 200 и JSON, например `{"recommendation":"Проверить результат DNS на клиенте","confidence":"medium"}`. Допустимые уровни уверенности: low, medium, high. Рекомендация выводится как текст. Лимиты составляют один одновременный запрос, восемь секунд, 8192 байта ответа и 4096 байт текста рекомендации. При недоступности адаптера панель показывает локальное объяснение. Адаптер или модель устанавливается оператором отдельно.

## Удалённая диагностика

Как в Windows-версии: на вкладке «Диагностика» → «Удалённая диагностика» → «Включить» (на 1 час … неделю,
потом выключается сама). Появляются адрес и токен, их можно скопировать или скачать файлом. Доступ — на порту
веб-интерфейса (8765) с заголовком `X-Token`; пути те же, что в Windows-версии, поэтому `RemoteDiag.ps1`
работает без изменений:

    .\RemoteDiag.ps1 -Address 192.168.1.50:8765 -Token …
    curl -H "X-Token: …" http://192.168.1.50:8765/bundle

`/status /check /diag /decisions /net /system /files /logs /bundle /cmd`. По умолчанию подключаться можно
только из домашней сети и от клиентов WG-Server; «откуда угодно» включается отдельно (нужен проброс порта).
Токен даёт только чтение и не открывает веб-интерфейс. Команды (`/cmd?c=meduza.reconnect`, `fix:<проверка>`,
`diagrun`) работают, только если разрешены, и только безопасные: действия с пометкой «опасно» или с вводом
данных (выход из аккаунта, смена ключей, создание сервера заново) удалённо недоступны никогда. Ключи WireGuard,
токены, пароли и QR-коды в отчётах вырезаются. Каждый запрос виден в таблице «Последние запросы» и в журнале.

## Что проверить на стенде

1. **MeduzaVPN.** Ответы `meduzavpn status --json`, `list --services --json`, `list --protocols --json`,
   `devices list --json`, `version`; коды выхода; имя сетевого интерфейса туннеля; работает ли ULTRA в пакете без графики;
   не перехватывает ли служба весь трафик шлюза сама. Команды и имена полей взяты из справки и строк
   CLI 1.2.80 (`meduzavpn-linux-amd64.tar.gz`), сам CLI не запускался.
   - `login --qr --json`: какие строки печатает (ссылка `verify_url`, `user_code`, `expires_in`), чем заканчивается
     при подтверждении и отказе на телефоне.
   - `login --email … --password-stdin`: текст ошибки при неверном пароле.
   - `profile --service … --protocol …`: не занимает ли запрос профиля место устройства на аккаунте и не выдаёт ли
     сервер каждый раз новый профиль. Агент запрашивает профиль один раз на VPN и запоминает адрес (`data/meduza-ping.json`).
   - Пинг до серверов: проходит ли `ping -I <интерфейс провайдера>` и TCP-соединение мимо туннеля, когда туннель
     подключён и включён kill switch.
   - Kill switch по умолчанию: включён ли он без `config.json`. На шлюзе его нужно выключить (проверка в диагностике).
   - `config set exclude_routes …` / `config unset …`: применяется ли к работающему туннелю или только при подключении.
   - Обновление: пакет `meduzavpn_<arch>.deb` из `release.json`, сверка sha256, `dpkg -i`; автообновление по умолчанию выключено.
2. **AmneziaWG.** Установка модуля ядра на выбранной версии Ubuntu; формат `awg show <имя> latest-handshakes`.
3. **zapret2.** Путь к `nfqws2` и папке `lua`; рабочие параметры стратегий; номер очереди.
4. **Маршруты.** Применение сценария на настоящем ядре; обратный путь пакетов (`rp_filter`); MTU через туннели.
5. **WG-Server.** `wg syncconf`, проброс порта, DNS для клиентов; `wg show <имя> listen-port`;
   перезапуск `wg-quick@` после смены подсети, MTU и ключа; строки PostUp/PostDown, перенесённые правкой файла.
6. **Удалённая диагностика.** Порт 8765 открыт в брандмауэре Ubuntu (если включён `ufw`); команды отчётов
   `/net` и `/system` (`ss`, `resolvectl`, `journalctl -k`) есть в установленной системе; адрес шлюза в данных
   для подключения определяется верно.
